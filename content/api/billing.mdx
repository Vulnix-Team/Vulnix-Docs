---
title: Billing
description: Read the plan, credit balance, and ledger history — so automation can check it can afford to run before it tries.
---

Billing over the API is **read-only**. There is a `billing:read` scope and no `billing:write`,
because nothing a token can do should be able to move money.

The reason to reach for these endpoints is the one that matters in CI: checking you can afford
a run *before* starting one, so a pipeline fails with a clear message instead of a
`422 credits_exhausted` halfway through.

## Plans

`GET /billing/plans` · scope `billing:read` · no minimum role

Every plan available, not just yours.

```json
{
  "plans": [
    {
      "id": "…",
      "name": "…",
      "monthly_price_usd": 0,
      "monthly_credits": 0,
      "is_self_serve": true
    }
  ]
}
```

    id: { type: "string", description: "Plan identifier." },

## Current status

`GET /billing/status` · scope `billing:read` · role `viewer`

The endpoint to poll before spending. Two shapes — check `is_exempt` first.

An exempt organization returns exactly this and nothing else:

```json
{ "is_exempt": true }
```

Everyone else:

<TypeTable
  type={{
    is_exempt: { type: "boolean", description: "`false` here. When `true`, no other field is present." },
    plan: { type: "object | null", description: "The current plan object, or null if none." },
    is_trial: { type: "boolean", description: "Whether this is a free trial. Drives [withheld detail](/api/conventions#withheld-detail-on-the-free-trial)." },
    trial_ends_at: { type: "string | null", description: "ISO 8601." },
    subscription_status: { type: "string | null", description: "Subscription state." },
    current_period_start: { type: "string | null", description: "ISO 8601." },
    current_period_end: { type: "string | null", description: "ISO 8601. When monthly credits refresh." },
    cancel_at_period_end: { type: "boolean", description: "Whether the subscription lapses at period end." },
    grace_period_ends_at: { type: "string | null", description: "Set after a failed payment — work still runs until this passes." },
    monthly_balance_usd: { type: "number", description: "Plan credits left this period. Spent first, and they do not roll over." },
    topup_balance_usd: { type: "number", description: "Purchased credits. Spent after monthly credits, and they persist." },
    credit_balance_usd: { type: "number", description: "The two above added together — the number to compare against a run's price." },
  }}
/>

<Callout type="warn" title="`is_exempt: true` means the other fields are absent, not zero">
  Demo and internal organizations return only `{ "is_exempt": true }`. Code that reads
  `credit_balance_usd` unconditionally will throw on them. Check `is_exempt` first and treat it
  as "spending is not limited here".
</Callout>

### Monthly credits are spent before top-up credits

`monthly_balance_usd` resets at `current_period_end` and does not carry over.
`topup_balance_usd` persists until spent. So a healthy-looking `credit_balance_usd` can still
be about to shrink at the period boundary — if you are scheduling work near it, read the two
components, not just the total.

## Ledger history

`GET /billing/history` · scope `billing:read` · role **`admin`**

Every credit movement, for reconciliation and per-team cost attribution.

```json
{
  "history": [
    {
      "id": "01M2NP…",
      "delta_usd": -5.0,
      "balance_after_usd": 95.0,
      "reason": "run_debit",
      "source_type": "run",
      "source_id": "01M2NP4K8QW3ZR7YT2XVB9CDEF",
      "created_at": "2026-09-16T18:04:11.229104+00:00"
    }
  ]
}
```

<TypeTable
  type={{
    delta_usd: { type: "number", description: "Negative for a charge, positive for a grant or top-up." },
    balance_after_usd: { type: "number", description: "Running balance after this entry." },
    reason: { type: "string", description: "Why it moved — `run_debit` for a pentest, for example." },
    source_type: { type: "string | null", description: "What caused it, such as `run`." },
    source_id: { type: "string | null", description: "The id of that thing. For a run charge this is the run id — or the `idempotency_key` you supplied when starting it." },
    created_at: { type: "string", description: "ISO 8601." },
  }}
/>

Because `source_id` carries the `idempotency_key` you chose, deriving that key from something
meaningful — a deploy id, a service name, a team prefix — turns this ledger into a cost
breakdown you can group without any extra bookkeeping.

## Console-only billing endpoints

Anything that moves money is unreachable with a token, whatever scopes it carries. All return
`403 api_token_route_not_allowed`:

<TypeTable
  type={{
    "POST /billing/checkout/subscription": { description: "Start a plan checkout." },
    "POST /billing/checkout/topup": { description: "Buy additional credits." },
    "POST /billing/portal": { description: "Open the Stripe billing portal." },
    "POST /billing/subscription/auto-renewal": { description: "Turn auto-renewal on or off." },
    "POST /billing/subscription/upgrade": { description: "Change plan." },
  }}
/>

Starting a pentest *does* spend credits and *is* available with `runs:write` — that is the
automation people actually need, and its cost is bounded and predictable. Changing what you owe
every month is not. See
[what tokens cannot do](/api/authentication#what-tokens-cannot-do).

## Checking affordability before a run

```bash
BALANCE=$(curl -fsS https://api.vulnix.dev/billing/status \
  -H "Authorization: Bearer $VULNIX_TOKEN" \
  | jq 'if .is_exempt then 1e9 else .credit_balance_usd end')

ESTIMATE=$(curl -fsS "https://api.vulnix.dev/scopes/$SCOPE_ID" \
  -H "Authorization: Bearer $VULNIX_TOKEN" | jq '.estimated_cost_usd')

if (( $(echo "$BALANCE < $ESTIMATE" | bc -l) )); then
  echo "Not enough credits: have $BALANCE, need about $ESTIMATE" >&2
  exit 1
fi
```

`estimated_cost_usd` on the [scope](/api/scopes#the-scope-object) is an estimate, not the exact
charge — leave headroom rather than comparing to the cent.
