---
title: Billing
description: Read the plan, the pentests and PR reviews left, and ledger history, so automation can check there is a pentest left before it starts one.
---

Billing over the API is **read-only**. There is a `billing:read` scope and no `billing:write`,
because nothing a token can do should be able to move money.

The reason to reach for these endpoints is the one that matters in CI: checking you have a pentest
left *before* starting one, so a pipeline fails with a clear message instead of a
`422 credits_exhausted` halfway through.

<Callout type="info" title="Two kinds of plan">
  Free, Builder, Startup and Pro are counted in **pentests and PR reviews** (`pricing: "units"`).
  Starter, the earlier Pro plan and Enterprise are billed in **credits** (`pricing: "credits"`).
  See [Plans & Billing](/billing-and-credits). Read `pricing` first and use the fields that go
  with it.
</Callout>

## Plans

`GET /billing/plans` · scope `billing:read` · no minimum role

Every plan available, not just yours.

```json
{
  "plans": [
    {
      "id": "…",
      "name": "…",
      "monthly_price_usd": 0,
      "monthly_credits": 0,
      "is_self_serve": true,
      "pricing": "units",
      "monthly_pentests": 0,
      "monthly_pr_reviews": 0
    }
  ]
}
```

## Current status

`GET /billing/status` · scope `billing:read` · role `viewer`

The endpoint to poll before spending. Two shapes — check `is_exempt` first.

An exempt organization returns exactly this and nothing else:

```json
{ "is_exempt": true }
```

Everyone else:

<TypeTable
  type={{
    is_exempt: { type: "boolean", description: "`false` here. When `true`, no other field is present." },
    plan: { type: "object | null", description: "The current plan object, or null if none." },
    is_trial: { type: "boolean", description: "Whether the organization is on the Free plan. Drives [withheld detail](/api/conventions#withheld-detail-on-the-free-trial)." },
    trial_ends_at: { type: "null", description: "Always null. Free doesn't expire; kept so existing clients don't break." },
    pricing: { type: "string", description: "`units` on Free, Builder, Startup and Pro; `credits` on Starter, the earlier Pro and Enterprise." },
    pentests: { type: "object | null", description: "`{ left }`: pentests you can still start. Null on `credits` plans." },
    pr_reviews: { type: "object | null", description: "`{ used, included, resets_at }`: PR reviews this month and when the count resets (ISO 8601). Null on `credits` plans." },
    subscription_status: { type: "string | null", description: "Subscription state." },
    current_period_start: { type: "string | null", description: "ISO 8601." },
    current_period_end: { type: "string | null", description: "ISO 8601. When the monthly allowance (or monthly credits) refresh." },
    cancel_at_period_end: { type: "boolean", description: "Whether the subscription lapses at period end." },
    grace_period_ends_at: { type: "string | null", description: "Set after a failed payment — work still runs until this passes." },
    monthly_balance_usd: { type: "number", description: "`credits` plans: plan credits left this period. Spent first, and they do not roll over." },
    topup_balance_usd: { type: "number", description: "`credits` plans: purchased credits. Spent after monthly credits, and they persist." },
    credit_balance_usd: { type: "number", description: "`credits` plans: the two above added together, the number to compare against a run's price. On `units` plans use `pentests.left`." },
  }}
/>

<Callout type="warn" title="`is_exempt: true` means the other fields are absent, not zero">
  Demo and internal organizations return only `{ "is_exempt": true }`. Code that reads
  `pentests` or `credit_balance_usd` unconditionally will throw on them. Check `is_exempt` first and treat it
  as "spending is not limited here".
</Callout>

### Allowances reset at the period boundary

On `units` plans, `pentests.left` is topped up to the plan's allowance at `current_period_end`, and
unused pentests don't carry over. `pr_reviews.used` goes back to zero at `pr_reviews.resets_at`:
the end of the billing period on a paid plan, the end of the calendar month on Free.

On `credits` plans, `monthly_balance_usd` resets at `current_period_end` and does not carry over.
`topup_balance_usd` persists until spent. So a healthy-looking `credit_balance_usd` can still
be about to shrink at the period boundary — if you are scheduling work near it, read the two
components, not just the total.

## Ledger history

`GET /billing/history` · scope `billing:read` · role **`admin`**

Every ledger movement, for reconciliation and per-team cost attribution. On `units` plans a pentest
is recorded as a fixed internal amount, so count `run_debit` entries rather than summing them. PR
reviews on those plans come from the monthly allowance and don't appear here.

```json
{
  "history": [
    {
      "id": "01M2NP…",
      "delta_usd": -5.0,
      "balance_after_usd": 95.0,
      "reason": "run_debit",
      "source_type": "run",
      "source_id": "01M2NP4K8QW3ZR7YT2XVB9CDEF",
      "created_at": "2026-09-16T18:04:11.229104+00:00"
    }
  ]
}
```

<TypeTable
  type={{
    delta_usd: { type: "number", description: "Negative for a charge, positive for a grant or top-up." },
    balance_after_usd: { type: "number", description: "Running balance after this entry." },
    reason: { type: "string", description: "Why it moved — `run_debit` for a pentest, for example." },
    source_type: { type: "string | null", description: "What caused it, such as `run`." },
    source_id: { type: "string | null", description: "The id of that thing. For a run charge this is the run id — or the `idempotency_key` you supplied when starting it." },
    created_at: { type: "string", description: "ISO 8601." },
  }}
/>

Because `source_id` carries the `idempotency_key` you chose, deriving that key from something
meaningful — a deploy id, a service name, a team prefix — turns this ledger into a cost
breakdown you can group without any extra bookkeeping.

## Console-only billing endpoints

Anything that moves money is unreachable with a token, whatever scopes it carries. All return
`403 api_token_route_not_allowed`:

<TypeTable
  type={{
    "POST /billing/checkout/subscription": { description: "Start a plan checkout." },
    "POST /billing/checkout/topup": { description: "Buy additional credits. `credits` plans only: on `units` plans it returns `topup_requires_active_plan`." },
    "POST /billing/portal": { description: "Open the Stripe billing portal." },
    "POST /billing/subscription/auto-renewal": { description: "Turn auto-renewal on or off." },
    "POST /billing/subscription/upgrade": { description: "Change plan." },
  }}
/>

Starting a pentest *does* use a pentest (or credits) and *is* available with `runs:write` — that
is the automation people actually need, and its cost is bounded and predictable. Changing what you owe
every month is not. See
[what tokens cannot do](/api/authentication#what-tokens-cannot-do).

## Checking affordability before a run

On Free, Builder, Startup and Pro, one pentest is one pentest, whatever the scope:

```bash
LEFT=$(curl -fsS https://api.vulnix.dev/billing/status \
  -H "Authorization: Bearer $VULNIX_TOKEN" \
  | jq 'if .is_exempt then 1e9 elif .pricing == "units" then .pentests.left else -1 end')

if [ "$LEFT" = "0" ]; then
  echo "No pentests left this month" >&2
  exit 1
fi
```

On Starter, the earlier Pro plan and Enterprise (`pricing: "credits"`), compare the credit balance
with the scope's estimate instead:

```bash
BALANCE=$(curl -fsS https://api.vulnix.dev/billing/status \
  -H "Authorization: Bearer $VULNIX_TOKEN" \
  | jq 'if .is_exempt then 1e9 else .credit_balance_usd end')

ESTIMATE=$(curl -fsS "https://api.vulnix.dev/scopes/$SCOPE_ID" \
  -H "Authorization: Bearer $VULNIX_TOKEN" | jq '.estimated_cost_usd')

if (( $(echo "$BALANCE < $ESTIMATE" | bc -l) )); then
  echo "Not enough credits: have $BALANCE, need about $ESTIMATE" >&2
  exit 1
fi
```

`estimated_cost_usd` on the [scope](/api/scopes#the-scope-object) is an estimate, not the exact
charge — leave headroom rather than comparing to the cent.
