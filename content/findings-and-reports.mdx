## Anatomy of a finding

Every finding carries the same core shape, regardless of scan type:

## Working a finding

<Steps>
<Step>

### Triage

Findings land on the **Findings** page, filterable by severity and status, with free-text search and
repo/domain filters. Update a finding's status inline as your team works through it.

</Step>
<Step>

### Resolve, snooze, or accept the risk

Mark a finding **fixed** once you've addressed it, **snooze** it to revisit later, or formally
**accept the risk** — every one of these actions is audited: who, and when.

</Step>
<Step>

### Validate the fix

Don't just trust that a fix worked — **Validate Fix** is a separate, narrowly-scoped run that
replays the *exact original exploit* against just that finding's asset, confirming the fix
actually holds before you close it out. This isn't a status toggle; it's a real re-test.

</Step>
<Step>

### (Whitebox only) Create a Fix PR

For an eligible Whitebox finding, open a real GitHub pull request with the engine-derived fix
already applied — a manual, per-finding action, not automatic.

<Callout type="warn" title="Free plan">
  Creating a Fix PR for a critical or high severity finding requires a paid plan — the same
  restriction that applies to full finding detail on a Free workspace.
</Callout>

</Step>
</Steps>

## Reports

Every run produces a PDF report you can download from `/reports`: a shareable, human-readable document for
stakeholders, with the findings, the steps to reproduce each one and how to fix it.

### Comparing runs over time

`/reports/compare` diffs findings across two runs of the same scope — the fastest way to show a
stakeholder real remediation progress between two points in time, rather than re-reading two
separate reports side by side.
